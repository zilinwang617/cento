# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Prototype-specific decisions

- The latest source of truth is Figma `RNdrvPrcyNqPQ32ICmm4Pa`, Desktop - 3 (`1:21`), 1440 × 1024. The earlier single-strip wood scene is superseded.
- The page is US Letter. `ARTBOARD` derives its width from the 8.5:11 proportion against a fixed height of 888, which leaves an even 68px above and below in the 1024-tall world; Figma's 686 was 0.026% off, so the number is computed rather than copied. Both CSS sheets read it through `--page-*` custom properties instead of repeating the figures — the page size is changed in one place.
- The PNG export is a whole 8.5 × 11 inches at `EXPORT_DPI` (300), so 2550 × 3300. Derive the scale from one edge and apply it to both, so the export can never drift out of proportion with the page. Canvas shadow offset and blur ignore the transform, so they stay multiplied by that scale.
- Use the current Figma cream page / cobalt strips as the default; keep the attached screenshot's teal page / cream strips as the Tidal palette.
- Original (the first style) uses #2D4793 for note paper, with white ink; this applies to sidebar notes, page notes, palette previews and export.
- Style backgrounds now follow Colors & Typography (`21:10`): Original, Tidal, Lilac, Poppy, Midnight, then Black & White last. Use the locally saved Figma paper textures with the original fill colors and opacities (50%, 20%, 15%, no texture, 20%, 54%). Black & White uses the Figma frame's #464646 beneath its translucent texture, gray strips and dark ink. Page, palette previews and PNG export share these settings and centered cover cropping; existing colored strip palettes stay unchanged.
- Preserve the Figma object imagery and fonts: Pacifico for Change Style. Exact source assets and licensed fonts are stored locally. Special Elite is no longer the only strip face — see the typeface library below.
- Strips are set in five faces taken from Figma `Colors & Typography` (`21:10`): Special Elite (display), Charmonman (handwritten), Libre Baskerville (serif), Poppins and Lexend Giga (sans). Lato held the second sans slot first, was dropped on sight — it read as ugly on paper — and Lexend Giga replaced it in the frame. A capture's `typography.category` selects the pool and each piece draws one face at random from it; source categories the library cannot answer — mono, mixed, unknown — collapse to `other` and draw from the whole library. The draw is stored on the note as `typeface`, so it survives reloads and export, and cut halves inherit their parent's face. Notes with no stored face (demo data, pre-typeface documents) get a draw seeded from their note ID rather than a fixed default.
- Special Elite stays a local file; the other four load from the Google Fonts CDN, so every stack ends in a same-category system fallback and an offline side panel degrades instead of collapsing to one face.
- Each face is set at the size that balances it against the others, following the Figma frame's own choice: Libre Baskerville, Poppins and Lexend Giga run at 15/16 of the base, the other two at the base itself. Lexend Giga sets 1.36× wider than Poppins at the same size, which is why splitting measures against the widest face in the pool rather than the drawn one — a piece cut to fit Poppins would overflow the strip in Lexend Giga. `referenceSize()` is the single source for that, and nothing should hardcode 18.
- Cutting never changes type size. A cut half keeps the size its parent was printed in, and `displayFontSize()` returns it untouched; only a strip the tray packs narrower than it was built gives any of it back. Shrinking a half to fit a flat 34px of padding it never had is what reduced short cuts — narrowest faces worst — to a few pixels.
- The handwritten face is set at 700. Charmonman's regular is a hairline next to the others and does not read as ink at strip size. Weight travels with the face through `fontWeight()` and the `--type-weight` custom property, so the Google Fonts request, the canvas measurements and the PNG export all agree.
- Charmonman's current size is 18px in workspace coordinates, retaining weight 700, following the user's adjustment back from the 22px trial. Its explicit size bypasses the Figma/base ratio. Existing handwritten notes update their stored font size and scale paper width and cut text offsets together; `typefaceSize` records the applied reference so reloads and cuts never repeat the adjustment. New captures record the same reference. Only actual tray width constraints or text overflow may still require fitting.
- Selectively retain opaque paper, subtle CSS texture and contact shadows, grip-aware lift / landing motion. Do not carry over the transparent wood-paper aesthetic or add a physics engine.
- Scissors toggle cutting mode (not a text-input dialog). In cutting mode the large scissors fade, the cursor is a small pair of scissors, and only the hovered word gap gets a cut indicator. Clicking it splits the strip in place, retaining text positions and rotation. This works in both the left tray and the right page. Escape or clicking scissors again restores grab / drag mode.
- Cutting targets should be forgiving and immediate: a 16-screen-pixel acquisition radius, 22-pixel release radius, and 8-pixel paper-edge tolerance. Keep a single nearest-gap indicator, no hover delay or guide animation; cache text metrics instead of re-measuring each pointer movement.
- Double-clicking empty left-tray space opens the existing text input. Change Style changes the palette, and Export saves only the composed page. No backend, persistence or deployment is required.
- Target the desktop experience only; do not create or QA a dedicated mobile layout.
- Libraries are allowed; the user does not require a native-CSS-only implementation. Prioritize showing a working visual iteration before exhaustive debugging unless asked otherwise.
- Paper strips should not show a dashed focus outline when clicked or dragged; use the existing lift and shadow as drag feedback.
- A strip picks up a tilt the moment it comes off the tray onto the desk. The angle is dealt from `TILT_LIBRARY`, a hand-set deck of ten magnitudes a side following a normal curve's quantiles — 0.3, 0.7, 1.1, 1.5, 1.9, 2.4, 3, 3.8, 5.2, 8 — which puts σ at 3.6, 2σ at ±7° and a hard ceiling of 8°. Five of the ten are under 2°; the 8° is the one strip per deck that really got thrown. Tune the look by moving a number in that list, not by reaching for a formula.
- Deal the deck, do not roll each strip independently: shuffle all twenty cards, hand them out one at a time, reshuffle when spent, and never repeat across the seam. Twenty strips then use every angle exactly once, so the spread on the page is the spread that was designed instead of whatever i.i.d. draws happened to cluster into. A grid of near-identical angles reads as a mistake; this cannot produce one.
- Repositioning a strip already on the desk keeps the tilt it landed with — a nudge must not re-roll it, or nothing can ever be placed deliberately. The tray always packs straight, so dragging a strip back and out again is what asks for a new angle. Re-fit the position after tilting: a rotated strip claims more room than the flat one the drag was constrained against.
- The future Chrome Extension sidebar is a scrollable, automatically sorted linear inbox. Its item sequence must stay consistent with the corresponding sequence on the main website. New captures follow one shared deterministic sorting rule; cutting replaces the original item in place with its left and right children in text order, while deletion removes the item without disturbing the relative order of the remaining items.
- The Extension MVP should offer drag-to-collect plus a context-menu fallback, with no keyboard shortcut. Main-site cuts and deletions sync back to the sidebar, while spatial composition state such as position, rotation, and z-order remains main-site-only.
- The main website's left sidebar uses an explicit note-ID sequence, independent of x/y coordinates and z-index. New batches go first (newest first), retaining reading order within a batch; manual drag reordering updates the stored sequence. Cuts replace the parent in place with left/right children. Use sequential, variable-width row packing with fixed horizontal and vertical gaps, no overlap and no backfilling that changes sequence; sidebar strips rest straight. Overflow scrolls vertically, with placeholder/reflow feedback and edge autoscroll during dragging. Canvas composition stays spatial. These sidebar layout rules supersede the earlier in-place cut-position rule for sidebar strips only.
- The bin comes from Figma Desktop - 5 (`19:7`) at 1245, 404, 185 × 301, matching its Desktop - 3 placement. Dropping a strip on it deletes the strip outright: there is no undo, no confirmation step and nothing is retained to restore. The hit area is forgiving on the three sides facing empty desk and tight on the left, so a strip resting against the page's right edge is never mistaken for a throw-away. Escape still cancels a drag held over the bin. Delete or Backspace on a focused strip is the keyboard equivalent.
- Run extension acceptance checks in Google Chrome, not Arc; Arc-specific side-panel behavior can hide Chrome Extension bugs.
- The Extension minimum is Chrome 116 because context-menu auto-open depends on `chrome.sidePanel.open()`; the base Side Panel API exists in 114, but that method does not.
- Main-site sidebar notes follow the active style's strip and ink colors, just like page notes. Keep those colors during dragging and cutting as well; position and legacy colorSource values must not switch a strip back to the fixed blue/white palette.
- All main-site note text sits 1px below its previous vertically centered position, including sidebar and cut pieces. PNG export adds the same 1px downward shift to its existing baseline compensation (fillText y is now 2).
